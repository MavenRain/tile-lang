**Minimal-span denotational design of TileLang (Conal Elliott style)**

TileLang is a Python-embedded DSL (on TVM) for high-performance AI kernels. Its essential idea is first-class *tiles* (shaped data chunks owned by parallel units such as thread blocks or warps) together with explicit dataflow operators, while memory hierarchy, layouts, thread binding, and pipelining are largely decoupled and treated as scheduling or realization choices.

Following Elliott, we give a simple mathematical model of the types, define the primitives so that they act on those meanings, and require that the meaning homomorphism preserves the algebraic structure of the domain (type-class morphisms). The result is a precise, compositional specification free of operational entanglement; correctness of any implementation is exact agreement with the denotation.

### Semantic model

The central type is a tile (or tensor) of shape \(S\) and element type \(A\):
\[
\llbracket \text{Tile}_S\, A \rrbracket = S \to A
\]
where \(S\) is a finite multi-index set (a product of integer intervals). A kernel denotes a pure function from input tiles to output tiles:
\[
\llbracket \text{Kernel} \rrbracket : \prod_i (S_i \to A_i) \;\to\; \prod_j (T_j \to B_j).
\]

Memory scopes (global, shared, fragment/register) and all scheduling annotations (`Parallel`, `Pipelined`, layout inference, swizzling, thread binding, async copies, barriers, \ldots) are *not* part of the denotation. They select particular implementations of the same mathematical function. This is the minimal cut that keeps the design denotative.

### Minimal spanning primitives

The pure dataflow of TileLang is generated by the following operators (closed under ordinary function composition and the evident algebraic structure of function spaces). Their meanings are the obvious ones:

- **copy** (identity transport)  
  \[
  \llbracket \text{copy}\, t \rrbracket = \llbracket t \rrbracket.
  \]
  Scope changes are purely operational.

- **map** (elementwise / body of a `Parallel` loop)  
  \[
  \llbracket \text{map}\, f\, t \rrbracket = f \circ \llbracket t \rrbracket.
  \]
  This is the action of the functor \(S \mapsto (S \to -)\).

- **gemm** (tensor contraction / matrix multiply-accumulate)  
  \[
  \llbracket \text{gemm}\, a\, b \rrbracket(i,j) = \sum_k \llbracket a \rrbracket(i,k) \cdot \llbracket b \rrbracket(k,j)
  \]
  (or the obvious accumulate form into an existing tile). More generally any tensor contraction.

- **reduce** (fold)  
  \[
  \llbracket \text{reduce}\, (\oplus)\, e\, t \rrbracket = \bigoplus_{s \in S} \llbracket t \rrbracket(s)
  \]
  where \(\oplus\) is associative (and usually commutative, so that parallel or atomic realizations are valid).

- **view / slice** (tile extraction)  
  \[
  \llbracket \text{view}\, t\, \sigma \rrbracket = \llbracket t \rrbracket \circ \sigma
  \]
  where \(\sigma : S' \hookrightarrow S\) is an affine embedding of index spaces.

- **Kernel / grid** (outer parallel product)  
  The `T.Kernel` construct denotes the product, over the grid of block indices, of the independent per-tile functions. Each block operates on the appropriate sliced views of the global tensors.

Allocation of intermediates is simply the introduction of a local binding of a function \(S \to A\) (initially constant or free). All other constructs (`async_copy`, barriers, most atomics, software pipelining, layout annotations, \ldots) preserve the above meanings and are therefore outside the pure denotation. Atomics for commutative monoids are realizations of `reduce`; non-commutative atomics fall outside the pure model.

### Type-class morphisms and free laws

- Tiles form the functor \(S \mapsto (S \to -)\). The meaning of `map` is exactly the functor action, so the functor laws hold automatically.
- `gemm` is a bilinear morphism for the corresponding contraction structure; the usual associativity and linearity laws therefore hold for free.
- Kernel composition is ordinary function composition.

Consequently every well-typed TileLang dataflow program denotes a unique pure function on arrays, and any correct implementation (regardless of tiling strategy, memory hierarchy, or backend) must compute exactly that function.

### What the design achieves

The five or six generators above, closed under composition, span the meanings of all essential TileLang kernels (GEMM, FlashAttention, elementwise, reductions, \ldots). Everything else—scheduling, scopes, layouts, backend-specific intrinsics—is an implementation strategy that realizes the denotation efficiently. This is the minimal-span cut in Elliott’s sense: a precise, simple mathematical model that informs both use and implementation without entangling them, and that yields the expected algebraic laws for free.
